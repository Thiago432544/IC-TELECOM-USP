### F11 — o `accept()` congelava para sempre

**A causa.** O handshake que lê o `client_id` rodava na **thread do `accept()`**:

```python
def handle_client(client_socket, client_address):
    id_len = int.from_bytes(client_socket.recv(1), "big")   # bloqueante, SEM timeout
    client_id = client_socket.recv(id_len).decode()
    ...
    t = threading.Thread(target=client_worker, ...)          # a thread só nasce DEPOIS
```

O `settimeout` só era aplicado dentro do `client_worker`, que ainda não existia
nesse ponto. Se uma câmera completasse o handshake TCP e os bytes do ID nunca
chegassem — e o outro lado sumisse sem FIN nem RST, que é o que acontece quando
um CPE reinicia ou a Rasp trava em brownout — esse `recv(1)` bloqueava **para
sempre**. Sem `SO_KEEPALIVE`, o TCP nunca detectava. O laço inteiro parava.

**A correção.** O `handle_client` passou a só criar a thread; o handshake foi
para `client_session`, que roda dentro dela:

```python
def handle_client(client_socket, client_address):
    t = threading.Thread(target=client_session,
                         args=(client_socket, client_address), daemon=True)
    t.start()


def client_session(client_socket, client_address):
    try:
        prepare_socket(client_socket)          # timeout + keepalive ANTES de qualquer recv
        id_len = recv_exact(client_socket, 1)
        if not id_len:
            client_socket.close()
            return
        ...
```

```python
def prepare_socket(sock):
    sock.settimeout(SOCKET_TIMEOUT)
    sock.setsockopt(socket.SOL_SOCKET, socket.SO_KEEPALIVE, 1)
```

E o laço de aceitação deixou de morrer por erro de uma conexão. O original era:

```python
while True:
    try:
        sock, addr = srv.accept()
        handle_client(sock, addr)
    except:
        break          # qualquer erro encerra o servidor, em silêncio
```

Agora:

```python
def serve_forever(srv):
    while True:
        try:
            sock, addr = srv.accept()
        except (ConnectionResetError, ConnectionAbortedError):
            continue          # conexão morreu antes do accept: não mata o servidor
        except OSError:
            break             # listener fechado: encerra de verdade
        try:
            handle_client(sock, addr)
        except Exception as err:
            print("Erro ao aceitar conexao:", err)
            sock.close()
```

**Por que este é o achado mais importante da sessão.** Um servidor que congela a
porta de entrada e volta com um reinício qualquer produz exatamente a assinatura
que motivou o projeto: sumiços longos, retorno inexplicável, ninguém sabe o que
consertou. O README documenta buracos de set→dez/2025, 55 dias em abr–mai/2026,
27/jul→05/ago e 06→18/ago. O F11 é uma explicação estrutural para esse padrão.

Ele também explica por que o monitor sozinho não bastaria: durante o
congelamento, `D:\SPA_Data` e o `LOG_connections.txt` ficam **silenciosos** sobre
a câmera afetada. Sem erro, sem evento. Só ausência — que é por isso que o alarme
tem de disparar por ausência, não por erro.

### F12 — `recv` sem laço derrubava conexões vivas

**A causa.** `recv(n)` pode devolver **menos** que `n` bytes. O bloco de dados já
era lido em laço; o header e o nome não:

```python
header = client_socket.recv(4)
if not header or len(header) < 4:
    reason = f"[{client_id}] Header invalido, encerrando conexao"   # derruba
```

Duas coisas erradas aqui. A primeira: numa LTE com retransmissão, os 4 bytes
podem chegar partidos e a conexão morre sem motivo. A segunda, mais insidiosa:
`recv` devolve `b""` quando o **outro lado fechou** — ou seja, essa mensagem
misturava "header corrompido" com "a câmera foi embora", que são diagnósticos
opostos.

**A correção.**

```python
def recv_exact(sock, n):
    buf = b""
    while len(buf) < n:
        chunk = sock.recv(n - len(buf))
        if not chunk:
            break          # EOF: devolve o parcial, quem chama decide
        buf += chunk
    return buf
```

```python
header = recv_exact(client_socket, 4)
if len(header) < 4:
    reason = (f"[{client_id}] Cliente encerrou a conexao" if not header
              else f"[{client_id}] Header truncado ({len(header)}/4 bytes)")
```

Idem para `name_len` e `file_name`. **O log virou instrumento de diagnóstico:**

| Mensagem nova | Significado |
|---|---|
| `Cliente encerrou a conexao` | a câmera fechou no limite do frame — o `sendall` dela estourou os 6 s por congestão (F8) |
| `Header truncado (2/4 bytes)` | a câmera morreu no meio do header — brownout, queda de rádio |
| `Problema no frame: timed out` | 30 s de silêncio total — enlace morto |

## 7. A 106, a distância e a reflexão de dois raios

Informação trazida pela equipe: **a 106 é bem mais distante da eNodeB** que as
outras, e há suspeita de que a conexão dela fique mais estável **quando há navio
ancorado**. Nenhum navio ancorou desde o início do acompanhamento, então a
suspeita segue não verificada.

A distância é consistente com os 39% de entrega da 106 contra 100% da 102. E foi
essa informação que derrubou o achado 3.1 (seção 4).

### Por que um navio melhoraria o sinal

O mecanismo mais provável é contra-intuitivo. Enlace sobre água a 700 MHz sofre
do **modelo de dois raios**: o raio direto e o refletido na superfície do mar
chegam ao receptor com fases diferentes. A água é refletor quase perfeito em
ângulos rasantes, então a reflexão volta com amplitude alta e fase invertida — e
em certas geometrias os dois raios **se cancelam**. Quanto maior a distância e
mais baixa a antena, mais profundos e largos ficam esses nulos. A 106, sendo a
mais distante, é a que mais sofre.

**Um navio ancorado no caminho bloqueia o raio refletido.** Some o cancelamento,
sobra o raio direto — e o sinal melhora. O casco de aço também pode funcionar
como refletor especular e abrir um caminho NLOS adicional. Os dois efeitos
empurram na mesma direção do que a equipe observou.

**Consequência prática imediata, e barata:** alguns metros de altura no CPE da
106 deslocam o padrão de nulos e podem valer mais que qualquer mudança de
software. Vale conferir junto o apontamento — o Amplimax é direcional, e alguns
graus fora do azimute custam vários dB.

### Não é preciso esperar navio

O `D:\SPA_Data` tem histórico de pastas desde 2025. A contagem de frames por dia
por câmera é proxy direto da qualidade do enlace:

```powershell
$raiz = "D:\SPA_Data\Imagens_Porto"
Get-ChildItem $raiz -Directory | Sort-Object Name | ForEach-Object {
  $dia = $_.Name
  foreach ($cam in '102','105','106') {
    $p = Join-Path $_.FullName $cam
    $n = (Get-ChildItem -LiteralPath $p -File -ErrorAction SilentlyContinue | Measure-Object).Count
    [pscustomobject]@{ Dia = $dia; Cam = $cam; Frames = $n }
  }
} | Export-Csv "$env:USERPROFILE\Desktop\frames_por_dia.csv" -NoTypeInformation -Encoding UTF8
```

Enumera centenas de milhares de arquivos — rode numa janela separada, leva
minutos. O resultado cruza com o registro de atracações e fundeios do Porto de
Santos. Um dia com navio no caminho deve aparecer como pico isolado de frames da
106 **sem** pico correspondente na 102.

### Maré ou hora do dia?

O diário de 19/08 registra padrão horário forte na 106: 8–11 h com poucas quedas,
14–23 h com 40 a 76 por hora. Isso separa duas causas bem diferentes:

- **Padrão fixo no relógio** → não é maré. O ciclo de maré é de ~12 h 25 min e
  **desliza ~50 min por dia**. Fixo aponta para algo diurno: congestionamento da
  célula LTE, ou térmico (a 106 já tem subtensão confirmada — calor e fonte fraca
  combinam mal).
- **Padrão deslizando ~50 min/dia** → é maré. E maré mudando a altura da
  superfície refletora é o **mesmo mecanismo de dois raios** do navio, o que
  reforçaria muito a hipótese.

A linha de base por hora do dia que o `baseline.py` já constrói é exatamente o
instrumento. Depois de ~1 semana de dados, o deslizamento aparece ou não.

### O que só a Fase 3 resolve

RSRP/RSRQ do enlace da 106 **não são observáveis do PC**. O `monitor/cpe.py`
aponta para `192.168.10.101`, o CPE do lado do SPA — mede a ponta receptora, não
o rádio da 106. A qualidade do enlace dela só é legível de dentro dela, no CPE
`192.168.11.254` próprio.

O cliente H01 já prova que o caminho existe: é o que o `restart_router()` faz por
HTTP. Um agente da Fase 3 na 106 lendo o CPE dela a cada minuto, cruzado com
atracações e tábua de maré, resolve em semanas o que hoje depende de esperar um
navio aparecer.

**Isso reposiciona a Fase 3:** de "caixa-preta para post-mortem" para *o
instrumento que responde à pergunta do navio*.
